## БЛОК 0. Гигиена репозитория и секреты ⏱ ~30 мин

### Цель
Убрать главную уязвимость проекта: пароль от БД лежит в `appsettings.json` и уже ушёл в историю git. Любой интервьюер, открывший репозиторий, видит это первым делом.

### Теория (разобраться своими словами)
- Что такое ASP.NET Core **User Secrets** (`dotnet user-secrets`), где физически хранятся секреты на машине и почему они не попадают в git.
- Чем secrets отличаются от `appsettings.Development.json` (и почему второй вариант не спасает).
- Как конфигурация ASP.NET Core строит слои: appsettings.json → appsettings.{env}.json → user-secrets → env-переменные → аргументы командной строки. Кто кого переопределяет.
- Почему «удалить файл из git» недостаточно, если коммит уже был (история коммитов). Знай термин **BFG / git filter-repo** — на собесе достаточно объяснить проблему и решение словами.

### Задачи
1. Вынести строку подключения к PostgreSQL (как минимум пароль) и будущий ключ JWT из `appsettings.json` в user-secrets.
2. Сменить пароль пользователя БД на новый (старый считать скомпрометированным).
3. Убедиться, что после клонирования репо «на чистой машине» проект запускается по инструкции из README — напиши в README раздел «Как запустить» (5–10 строк: .NET 10, PostgreSQL, Redis, команда secrets init).

### Критерии приёмки
- [ ] В файлах репозитория нет ни одного пароля.
- [ ] Проект запускается локально, БД подключается.
- [ ] Можешь устно ответить: «где хранятся секреты в dev? а в проде?».

## БЛОК 1. Быстрые багфиксы и чистота кода ⏱ ~2–3 часа

### Цель
Устранить фактические баги и следы копипасты. Это то, что находят за 5 минут чтения кода, и то, что роняет впечатление сильнее всего.

### Теория
- **Structured logging**: почему `_logger.LogWarning(ex, $"...{x}")` хуже, чем шаблон `"Ошибка: {Message}", x` (серчабельность логов, провайдеры, cost). Пойми концепцию message templates.
- **Информация в ответах об ошибках**: что можно отдавать клиенту в dev и нельзя в prod (stack trace, внутренние сообщения). Принцип: детали — в лог, клиенту — общий текст.
- **HTTP-семантика**: какой статус корректен для успешного DELETE (и почему тело при этом не нужно).
- Правила именования в C#: методы PascalCase, приватные поля `_camelCase`, папка доменных сущностей обычно называется `Models` или `Entities`.

### Задачи
1. **Баг в аналитике**: найди в `AnalyticsService` расчёт среднего чека и исправь формулу (подсказка: сравни её с расчётом конверсии рядом — там скопирован лишний множитель). Проверь руками на данных.
2. Redis `InstanceName` — сейчас значение из другого проекта («OrderService»). Переименуй под этот проект.
3. Создай статический класс `CacheKeys` в `Common/`: все ключи кэша — через него. Заодно исправь баг: ключ summary-аналитики форматирует nullable-даты, которые ещё null → ключ получается невалидный. Значения по умолчанию должны подставляться ДО формирования ключа.
4. Мелочи нейминга: `cashedJson` → `cachedJson`; методы `setServiceRequestDb` и соседние — PascalCase; папку `Class/` переименуй в `Models/` и поправь namespace'ы.
5. Рефакторинг `ExceptionMiddleware`: structured logging; наружу не утекает `ex.Message` необработанного исключения (в dev — можно).
6. Все DELETE-ручки возвращают `204 NoContent`.
7. Опечатку `SheduledAt` → `ScheduledAt` исправь ВМЕСТЕ с миграцией на переименование колонки. Осознай, как EF делает rename колонки безопасно.

### Критерии приёмки
- [ ] `dotnet build` чистый, Swagger открывается, дашборд считает адекватные цифры.
- [ ] Можешь показать diff этого блока и объяснить каждую правку одной фразой.

## БЛОК 2. Response DTO + пагинация ⏱ ~полдня

### Цель
API не должно сериализовать EF-сущности с навигационными свойствами. Плюс списковые ручки должны уметь пагинацию.

### Теория
- Разница **Entity vs DTO** по сторонам границы приложения. Какие проблемы даёт возврат сущности: циклы навигации, утечка внутренних полей, жёсткая связанность контракта API со схемой БД, over-fetching.
- Паттерн пагинации: параметры запроса (page/pageSize или offset/limit), ограничение сверху pageSize, форма ответа `{ items, page, pageSize, totalCount }`. Почему `Skip/Take` транслируется в `OFFSET/LIMIT`.
- `AsSplitQuery()` — что такое cartesian explosion при нескольких `.Include()`, когда включать split query.
- Подумай про маппинг entity→dto: вручную vs AutoMapper. Для собеса честнее вручную — и сумей обосновать.

### Задачи
1. Response DTO для Client, Master, ServiceRequest (вложенность: заявка отдаёт краткую инфу о клиенте и мастере, без обратных ссылок).
2. Перевести GET-ручки списков и by-id на response DTO.
3. Пагинация на всех списках (clients, masters, requests): query-параметры page/pageSize, ответ с totalCount.
4. `AsSplitQuery()` там, где несколько Include — сумей объяснить, зачем именно в этом месте.
5. Фильтр по телефону клиента (поиск) — он понадобится фронту и хорошо смотрится на демо.

### Критерии приёмки
- [ ] Ни одна сущность EF больше не возвращается из контроллеров напрямую.
- [ ] `GET api/requests?page=2&pageSize=10&status=New` работает, totalCount корректен.
- [ ] JSON без циклов и без лишних полей (проверь глазами в Swagger).

## БЛОК 3. Статусная модель заявки (State Machine) ⏱ ~2–3 часа

### Цель
Заявку нельзя провести по несуществующему пути: закрыть дважды, отменить завершённую, назначить мастера отменённой. Сейчас `CompleteServiceRequest` молча перезапишет статус у любой заявки.

### Теория
- **Конечный автомат (FSM)** как модель бизнес-сущности: допустимые переходы New → Assigned → InProgress → Completed, и отдельно → Cancelled. Нарисуй таблицу переходов на бумаге ДО кода — она и есть ТЗ для метода.
- Где живёт бизнес-правило: в методе сущности (rich domain model) или в сервисе. Пойми trade-off, выбери одно и защищай выбор.
- Доменные исключения против возвращаемых кодов: почему `BadRequestException` с сообщением — идиоматично для твоей архитектуры с middleware.
- Идемпотентность повторного действия: что отвечать на повторное «завершить» (409 Conflict vs 400 — подумай и обоснуй).

### Задачи
1. Реализуй проверку допустимости перехода статуса при Update и Complete (недопустимый переход → BadRequestException с понятным текстом).
2. При Complete запрети отрицательные суммы, MasterPayout считай от комиссии конкретного мастера (`Master.CommissionPercent`), а не магическим `0.50m`. Если мастер не назначен — завершение запрещено.
3. При назначении мастера проверяй, что мастер существует и `IsActive` (неактивного назначать нельзя) — это уже описано в master-ТЗ как пример BadRequestException.
4. Сообщения об ошибках — через `ErrorMessages`.

### Критерии приёмки
- [ ] Сценарии «двойное завершение», «завершить без мастера», «отменить завершённую» возвращают 400/409 с человеческим сообщением.
- [ ] MasterPayout в закрытой заявке = процент назначенного мастера.

## БЛОК 4. JWT-аутентификация + роли + CORS ⏱ день

### Цель
Закрыть API. Роли: Admin (владелец/диспетчер) — всё; Master — только свои заявки и свои данные. Это самый частый блок вопросов на собесе middle/jun+.

### Теория (самая важная в этом ТЗ)
- **Authentication vs Authorization** — формулировка в одну фразу каждый.
- Устройство **JWT**: три части header.payload.signature, кто подписывает, что внутри claims, почему серверу не нужна сессия (stateless), срок жизни токена, где хранить на клиенте и основные риски (XSS/localStorage).
- Конвейер **JwtBearer**: как middleware валидирует подпись/expiry/issuer/audience, откуда берётся ключ.
- Хранение паролей: почему не в открытом виде, что такое соль, чем BCrypt/PBKDF2 лучше MD5/SHA «просто так». Не пиши свой хешер — возьми готовую библиотеку.
- **CORS**: same-origin policy браузера, preflight OPTIONS, чем отличается простые запросы от сложных, что настраивает политика.
- `[Authorize]`, `[Authorize(Roles = ...)]`, `AllowAnonymous` — механика атрибутов.

### Задачи
1. Сущность User (Id, Username, PasswordHash, Role, MasterId?), миграция, сид дефолтного админа.
2. `POST api/auth/login` → проверка пароля, выдача access token c claims (UserId, Role, Name, MasterId если есть). Настройки JWT (issuer/audience/key/lifetime) — из конфигурации, ключ в user-secrets (см. Блок 0!).
3. Регистрация authentication middleware в правильном порядке относительно authorization.
4. Закрой контроллеры: аналитика, бюджеты, мастера, клиенты — только Admin. Мастер читает только свои заявки (фильтр по claim MasterId в сервисе, а не в контроллере).
5. CORS-политика для localhost фронта.
6. `UseHttpsRedirection`.

### Критерии приёмки
- [ ] Без токена любой запрос → 401. Мастер не видит чужие заявки → 403/фильтрация.
- [ ] Можешь на собесе расшифровать свой же JWT на jwt.io и объяснить каждую часть.

## БЛОК 5. Индексы PostgreSQL + enum как строки ⏱ ~2 часа

### Теория
- Как устроен **B-Tree индекс**, когда он помогает (селективность, range-запросы) и когда бесполезен/вредит (низкая селективность, лишние записи при INSERT/UPDATE).
- **Составной индекс и правило крайнего левого префикса**: почему порядок колонок `(Status, CreatedAt)` ≠ `(CreatedAt, Status)` и какие запросы какой покроет. Подумай, какие реальные запросы из твоего AnalyticsService ложатся на составной индекс.
- PostgreSQL НЕ создаёт индексы на FK автоматически (в отличие от некоторых СУБД) — поэтому индексы на ClientId/MasterId/SourceId нужны руками. Умей это объяснить.
- Unique index vs обычный: телефоны клиентов и мастеров должны быть уникальными — это бизнес-правило на уровне БД.
- `EXPLAIN ANALYZE` — научись показывать «до/после» на одном запросе. Одна такая демонстрация на собесе стоит десяти слов.
- `JsonStringEnumConverter`: зачем человекочитаемые статусы в API (контракт с фронтом, отладка), и минус подхода (переименование элемента enum ломает контракт) — сумей упомянуть trade-off.

### Задачи
1. Индексы: составной (Status, CreatedAt); ScheduledAt; FK (ClientId, MasterId, SourceId); unique на PhoneNumber клиентов и мастеров; индекс на дату рекламных расходов.
2. Миграция `AddPerformanceIndexes` + `Update-Database`. Проверь в миграции, что unique-индексы реально UNIQUE.
3. JsonStringEnumConverter глобально в AddControllers.
4. Один раз прогони EXPLAIN ANALYZE по фильтру заявок до и после индекса — сохрани вывод, пригодится рассказать.

### Критерии приёмки
- [ ] `GET /api/requests?status=...` и дашборд работают быстрее либо хотя бы план использует Index Scan.
- [ ] Попытка создать двух клиентов с одним телефоном падает с понятной ошибкой (проверь, как middleware отформатирует DB-ошибку уникальности — возможно, нужен catch на PostgresException 23505 → ConflictException; это опционально, но сильно).

## БЛОК 6. Инвалидация кэша ⏱ ~1–2 часа

### Цель
Сейчас дашборд после закрытия заявки до 30–60 сек показывает старое. На живом демо это заметно и выглядит как баг.

### Теория
- TTL vs явная инвалидация: когда достаточно TTL, когда нужна инвалидация по событию.
- Cache stampede/thundering herd — термин знай хотя бы на уровне определения.
- Почему инвалидацию делают в сервисе (там, где меняются данные), а не в контроллере.

### Задачи
1. При создании/обновлении/закрытии заявки сбрасывай затронутые ключи кэша (дашборд сегодня + summary).
2. TTL оставь как страховку поверх инвалидации.

### Критерии приёмки
- [ ] Завершаешь заявку → сразу запрашиваешь дашборд → цифры свежие.

## БЛОК 7. Seeder тестовых данных ⏱ ~2 часа

### Цель
Демо на собесе: пустая база = провал. Нужны реалистичные данные за 30 дней.

### Теория
- Подходы к сидингу: при старте приложения (Environment-guarded hosted service) vs эндпоинт `POST /api/dev/seed`. Trade-offs: непреднамеренный засев прода, идемпотентность.
- Генерация реалистичных данных: библиотека Bogus или ручной генератор. Распределение статусов/дат должно давать осмысленную аналитику (конверсия не 0% и не 100%).

### Задачи
1. Сид: 3 источника с расходами, 3 мастера, 15 клиентов, ~50 заявок с разбросом дат за 30 дней, часть завершена с финансами.
2. Эндпоинт доступен только в Development.
3. Повторный вызов не должен плодить дубли (идемпотентность или очистка перед сидом — выбери и обоснуй).

### Критерии приёмки
- [ ] После сида дашборд и аналитика выглядят живо на скриншотах из docs/screens.
